# 開発の詳細

README の[開発](../README.ja.md#開発)の節を補う文書です。CI が確かめる内容、リリースの流れ、テストの範囲を説明します。

## CI が確かめること

CI (`.github/workflows/ci.yml`) は Linux と macOS で `make setup` と `make ci` を実行します。確かめる内容は手元の `make ci` と同じで、整形、clippy (警告はエラー扱い)、テストです。そのあと、リリースのワークフローが配るすべてのターゲットについてリリース版をビルドします。

cargo のコマンドはすべて `--locked` を付けて実行するので、ビルドとテストはコミット済みの `Cargo.lock` をそのまま使います。Makefile はこのフラグを `CARGO_FLAGS` (既定値 `--locked`) で渡します。

最低限必要な Rust の版 (`Cargo.toml` の `rust-version`) は、`mise.toml` で固定した Rust の版の `major.minor` です。CI もこの版でテストします。

統合テストは Cargo の `CARGO_BIN_EXE_safe-rm` を使い、そのプロファイルと出力先にビルドしたバイナリを実行します。リリース版を検証するには `mise exec -- cargo test --locked --release` を実行します。`CARGO_TARGET_DIR` でビルド先を変えることもできます。

公開 API の `GitChecker::check_directory()` と `check_directory_with_cache()` は、ディスク上から消えた未コミットの削除も拒否します。まず実在する子孫を調べ、続いて指定ディレクトリを起点に Git ステータスを 1 回走査します。内部の再帰処理ではこの走査を繰り返しません。回帰テストでは、孫にある staged・未ステージの削除と、名前の前方が一致する隣のディレクトリとの区別を確認します。

## リリースの流れ

リリースのワークフロー (**Actions → Release → Run workflow**) は、次の版 (`yy.m.counter`) を決め、版を上げるコミットとタグを `main` に push します。続いてそのタグから全ターゲットをビルドし、`safe-rm-<target>.tar.gz` と `SHA256SUMS` を公開します。dry run では版を決めて `Cargo.toml` と `Cargo.lock` の差分を表示するだけです。
